# Build plan 12 Oct 2026 – ToHuus Cloud, native iPhone app, assistant

This file is the shared contract for everyone (people and coding agents) working on this build. Strategy source: the Outline wiki, collection "ToHuus Hub / Fredirando", page "Ergebnis: ToHuus merkt sich, was zu Hause fehlt – Strategie ab 12.10.2026" ("Gilt jetzt"), plus Till's brief of 12 Oct 2026, 13:39.

## Product frame (binding)

ToHuus is the **shopping and household assistant** of a home: it remembers what is there, what is missing and what it costs, helps decide what to cook, and shows where the money for food and household goes. Three jobs, in this order:

1. **Einkauf** – remembers what is missing (purchase rhythm from receipts and ticks, no stock-keeping required), one shared list, shop mode.
2. **Kochen** – cook planner as an *output* of what is at home ("Daraus könnt ihr heute kochen"), week plan optional.
3. **Geld** – finance planner for groceries and household: spend per month, per shop, per category, price changes, budget, saving hints from the household's own receipts.

Whatever the household's digital level, it works: full grocery delivery (REWE eBon/avis), receipt photos (Aldi, Lidl, paper), or just talking/typing into the assistant ("Milch ist alle, und wir brauchen was für Sonntag").

**ToHuus is not** a family calendar, chat, task manager with responsibilities, points/gamification, nutrition or health log, tracking tool. Never build those.

Product rules from the strategy: capture is always on, upkeep is never required; suggestion instead of automation (derived items appear as suggestions with their origin, never silently on the list; dismissed twice → stop suggesting); every list row shows its origin; one onboarding question "Wer gehört dazu?" sets the view; the word "Gedächtnis" is internal only – outward the verb "merkt sich"; "KI" is never the promise.

## Two ways to run ToHuus

| | Self-hosted | ToHuus Cloud |
|---|---|---|
| Who | people with a server (Docker, Home Assistant) | everyone else, iPhone first, Android/browser via PWA |
| Server | this repo, `MULTI_TENANT=false`, one household | same image, `MULTI_TENANT=true`, many households |
| Price | free, AGPL, everything unlocked | Free / Haushalt / Plus (see plans) |
| AI | own key (`AI_*` env) or none | OpenRouter, pinned to Mistral, quota per plan |
| Apps | web/PWA and the iPhone app ("own server") | web/PWA and the iPhone app ("ToHuus Cloud") |
| LAN features | Home Assistant REST, printers, Telegram, IMAP, Cookidoo | off (HACS polling and MCP keep working) |

## Architecture decisions

1. **One encrypted SQLite file per household.** `DATA_DIR/households/<uuid>/tohuus.db` + `images/`. Library: `better-sqlite3-multiple-ciphers` (drop-in for `better-sqlite3`, SQLCipher-compatible cipher). No Postgres, no Supabase: the 80k-line codebase is synchronous better-sqlite3, and file-per-household isolates harder than row-level security.
2. **`db` becomes a proxy.** `AsyncLocalStorage` holds the household per request/job; `db` resolves to that household's connection (LRU pool). Without context in cloud mode every access throws. In self-host mode it is the single database, behaviour unchanged. Named migrations (`migrate(name, sql)`) are registered at module load and replayed on every household database when it is opened.
3. **Envelope encryption.** Each household has a random 256-bit data key (DEK). It is stored wrapped (AES-256-GCM) with the master key (`TOHUUS_MASTER_KEY`, 32 bytes base64, env only, never on the data volume) in `accounts.db`. `accounts.db` is itself encrypted with a key derived from the master key (HKDF, info `accounts`). Images on disk are AES-256-GCM with the household DEK. Deleting a household destroys its wrapped key first (crypto-shredding), then the folder. Self-host: `DB_ENCRYPTION_KEY` (optional, recommended); an existing plain database is converted on first start with the key set (backup kept until the encrypted copy is verified).
4. **Accounts directory** (`accounts.db`): accounts (email, scrypt password hash, passkeys, verified-at), memberships (account ↔ household, role, guest level, `expires_at`), households (uuid, name, form, region, lang, plan, trial_ends_at, wrapped DEK, created_at), app/device tokens, sessions, billing transactions, usage counters. Inside each household database the existing `users` table stays; a membership maps an account to a `users.id` in that household, so all existing code keeps working.
5. **Device tokens for apps.** Scope `app` = exactly the rights of the member, bound to a device name, listed and revocable under signed-in devices. Header `Authorization: Bearer sw_app_…`, household chosen with `X-Household: <uuid>` (cloud only; default = last used).
6. **AI via OpenRouter**, OpenAI-compatible. Every request carries `provider: { order: ["mistral"], allow_fallbacks: false, data_collection: "deny" }`. Env: `AI_BASE_URL` (default `https://openrouter.ai/api/v1`), `AI_API_KEY`, `AI_MODEL_TEXT` (default `mistralai/mistral-small-2603`), `AI_MODEL_VISION` (default `mistralai/mistral-small-2603`, receipts may use `mistralai/mistral-large-4-0`), `AI_MODEL_AUDIO` (default `mistralai/voxtral-small-24b-2507`). The old `VISION_*` variables keep working as fallbacks. Art. 9 data (allergies, children's birth years, anything flagged sensitive) never goes to a model without the household's explicit consent switch (`ai.health_share`, default off).
7. **Performance.** Route-level code splitting (React.lazy) so the first load is the shell + "Heute" only; target < 250 kB gzip for the initial JS. "Heute" loads one aggregated endpoint instead of many calls. Server: compression, ETags, no synchronous heavy work on request paths (image processing and AI in the background).

## Plans (hypotheses from the wiki, measured in the F&F test)

| Plan | What | Price |
|---|---|---|
| Free | shared list with shop mode, receipts unlimited (rate-limited), remembers 60 days back (rhythm, "Das habt ihr noch", week total), recipes by hand/link, export, 20 assistant messages/month | 0 € |
| Haushalt | full history (price history, spending, savings review), connected households, mirror to other lists, import quota (social, screenshot, paper list photo), 100 assistant messages/month | 3,99 €/month or 34,99 €/year |
| Plus | Haushalt + assistant in everyday use (week plan from the pantry, monthly analysis, substitute from stock), 1 500 messages/month fair use, throttled not blocked | 5,99 €/month or 59,99 €/year |
| Self-hosted | everything, own AI key | free |

- **Storage quota per household** (images, receipt files, database), enforced server-side on every upload and shown in settings: Free 250 MB, Haushalt 2 GB, Plus 5 GB, self-hosted unlimited (configurable `STORAGE_QUOTA_MB`). Exceeding it blocks new uploads with a clear message, never deletes anything. The quota is the lever for a later family-share/"Abo teilen" offer (several households under one subscription).
- One subscription **per household**; members, children, guests and the connected household never pay.
- 14-day trial at Plus level for every new cloud household, no payment data.
- When a subscription ends, the household falls back to Free; nothing is deleted.
- Apple product IDs: `de.heidrichdigital.tohuus.haushalt.monthly`, `…haushalt.yearly`, `…plus.monthly`, `…plus.yearly`; subscription group "ToHuus". `appAccountToken` = household UUID. Server verifies signed transactions (JWS, Apple root chain) and App Store Server Notifications v2 itself – no RevenueCat. Web payments (Mollie) later.
- No lifetime purchase with AI; no ads, no affiliate, no selling receipt data.

## API contract (new endpoints)

All JSON. Errors `{ error: string }` with 4xx/5xx.

Instance and auth (cloud and self-host):

- `GET /api/instance` (public) → `{ name, mode: 'cloud'|'selfhost', version, brand, lang, region, auth: { password, magicLink, passkey, oidc }, signup: boolean, features: { assistant, voice, receiptsAi, billingApple }, legal: { privacy, terms, imprint } }`
- `POST /api/auth/app` `{ email|name, password, device }` → `{ token, account?, user, households: [{ id, name, role, plan }], household }`. Also accepts an existing cookie session (`{ device }` only) and exchanges it.
- `GET /api/auth/app/devices`, `DELETE /api/auth/app/devices/:id`.

Cloud only:

- `POST /api/cloud/signup` `{ email, password, name, householdName, form: 'single'|'couple'|'family'|'wg'|'carer', lang, region, client: 'web'|'ios', device? }` → web: session cookie; ios: `{ token, household }`. Rate-limited, e-mail verification link sent (account usable before verification, but invites/export need it).
- `GET /api/cloud/me` → account, memberships, active household.
- `POST /api/cloud/households` (create another), `POST /api/cloud/households/:id/activate` (cookie sessions), `DELETE /api/cloud/households/:id` (admin; crypto-shred).
- `DELETE /api/cloud/account` (Apple 5.1.1(v)): leaves/deletes households as described in the wiki lifecycle.
- `GET /api/billing/status` → `{ plan: 'free'|'trial'|'haushalt'|'plus'|'selfhost', trialEndsAt, renewsAt, source: 'apple'|'none', limits: { historyDays, assistantPerMonth, ... }, usage: { assistantThisMonth, ... }, products: [...] }` (works in self-host too, returns `selfhost`).
- `POST /api/billing/apple/transaction` `{ signedTransaction }` → status.
- `POST /api/billing/apple/notifications` (App Store Server Notifications v2, public, JWS verified).

Features (both modes):

- `GET /api/today` → one aggregate for the "Heute" screen: greeting, rhythm suggestions due, list summary (open count, last changes with origin), "Das habt ihr noch" (expiring), cook idea for today, money this week/month, notices. Must answer in < 50 ms on a typical household.
- `GET /api/rhythm` → products with purchase rhythm (from receipts and list ticks, **no stock required**): `{ productId, name, everyDays, lastBought, dueOn, confidence: 'low'|'medium'|'high', origin: 'receipts'|'ticks'|'both', suggested }`. `POST /api/rhythm/:productId/accept` (puts it on the list with origin "merkt sich"), `POST /api/rhythm/:productId/dismiss`.
- `POST /api/assistant/chat` `{ message, conversationId? }` → `{ conversationId, reply, actions: [{ kind, summary, undo? }] }`. Tools run server-side (list add/remove/check, what is at home, rhythm, recipes from pantry, plan a meal, spending questions, remember/forget). Writes are reversible and reported in `actions`.
- `POST /api/assistant/transcribe` (multipart `audio`) → `{ text }` (Voxtral). `POST /api/assistant/voice` = transcribe + chat in one call.
- `GET /api/money/overview?month=YYYY-MM` → `{ month, total, budget, byCategory, byShop, byWeek, vsLastMonth, priceChanges: [...], hints: [...] }` built on `spending.ts`/`spend2.ts`.
- `GET /api/cook/ideas` → recipes cookable now / with 1–2 missing items, from pantry + rhythm, respecting allergies (server-side only).

Existing endpoints the apps use unchanged: `/api/shopping`, `/api/shop/*`, `/api/products`, `/api/stock/*`, `/api/recipes*`, `/api/plan*`, `/api/imports/*`, `/api/spend/*`, `/api/events` (SSE), `/api/me`, `/api/settings`.

## Navigation (web and iPhone)

Five tabs: **Heute · Einkauf · Vorrat · Kochen · Geld**. The assistant is a floating button (microphone + text) reachable from every tab. Settings, guests, Verwöhnen, displays, Home Assistant and everything else live behind "Mehr" (avatar/settings in the Heute header). The tab bar is **white** (light surface, dark icons, green active state), also in the PWA.

## iPhone app

SwiftUI, iOS 17+, bundle `de.heidrichdigital.tohuus`, folder `ios/` (XcodeGen `project.yml`). Native screens for the five tabs and the assistant; works offline for the list (local cache + operation queue, replayed via `/api/shop/sync`). Connect to "ToHuus Cloud" (default, sign up in the app) or "Eigener Server" (URL or QR). Share extension for receipts (PDF, screenshot, photo) and recipe links, VisionKit document scanner, barcode scanner, dictation (on-device speech, falls back to server transcription), StoreKit 2 paywall per household. Rare settings open the web UI in a `WKWebView` with the session. TestFlight first for Till and Lea (internal), then F&F as external group.

## Out of scope for this build

Calendar, chat, tasks with owners, points; bank account sync; scraping of retailer apps or Cookidoo in the cloud; iCloud mode; web payments; Android native app.
